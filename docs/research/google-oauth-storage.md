# Google OAuth storage: local Mac and hosted Django

Researched 24 November 2026 against official Google documentation and repository source. This is a targeted audit and proposed design, not a security certification. No credential contents, Keychain entries, mailbox data, or Cloud project settings were read. No application code or working connection was changed.

## Recommendation

Keep the current Desktop OAuth flow and macOS Keychain for this local, owner-only assistant. Google explicitly recommends platform credential storage, including macOS Keychain; servers holding many users' tokens should encrypt them at rest and keep the datastore private. A Django model containing plaintext tokens would not provide these protections. [Google OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices)

Django is the application framework, not the factor deciding the OAuth client type. A locally executed CLI can use Desktop OAuth; a hosted service accepting callbacks for remote users needs the web-server flow. Google's Desktop documentation describes public clients using the system browser and a local callback. [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app)

## Verified implementation

These findings concern the checked-in code, not the live configuration or OS access controls.

| Area | Implemented protection and evidence |
| --- | --- |
| Authorization | `GoogleClient.authorize()` accepts only Desktop configuration with approved Google authorization/token endpoints; rejects mixed web/Desktop configurations; explicitly enables PKCE; binds a random callback port to `127.0.0.1`; bounds consent and HTTP waits. [client.py](../../gmail/client.py) |
| Library behavior | The existing synthetic integration tests exercise the real OAuth library's S256 challenge/verifier, offline access, state mismatch rejection, denial, timeout, and insufficient-scope failure. Google's flow implementation supplies offline access and PKCE support. [Tests](../../tests/gmail/test_connection.py), [Google library source](https://googleapis.dev/python/google-auth-oauthlib/latest/_modules/google_auth_oauthlib/flow.html) |
| Secret storage | `KeychainStore` explicitly selects the macOS backend, with no plaintext fallback. Email and serialized credentials live in Keychain; the filesystem pointer contains only a slot number. Credentials are excluded from the connection dataclass representation. New directories/files request restrictive permissions. [credentials.py](../../gmail/credentials.py) |
| Failure preservation | Writes target the inactive Keychain slot before atomically replacing the pointer. Failed consent, account checks, scope checks, and credential writes preserve the previously active local connection. This cannot guarantee that Google leaves an old grant valid after every new authorization. [credentials.py](../../gmail/credentials.py), [service.py](../../gmail/service.py) |
| Account and scope binding | The service checks exact supported scope sets, a refresh token, and Google's token endpoint; verifies the actual Gmail profile against the requested address; requires explicit account replacement; and verifies the profile again before connected operations. `login_hint` alone is not trusted. [service.py](../../gmail/service.py) |
| Refresh and errors | Refresh is performed under a local exclusive lock, revalidated, and persisted. Existing tests exercise preservation when refresh omits a new refresh token, invalid grants, and changed scopes. Exceptions at the service boundary are sanitized. Profile/revoke calls have finite timeouts and disable redirects. [client.py](../../gmail/client.py), [service.py](../../gmail/service.py), [Tests](../../tests/gmail/test_connection.py) |
| Disconnect and isolation | Disconnect disables local access, attempts remote revocation, clears both known slots, and distinguishes unconfirmed revocation/cleanup failures. Factory keys separate configured owners and repository paths; this remains a single configured-owner factory, not tenant authorization. [service.py](../../gmail/service.py), [factory.py](../../gmail/factory.py) |

## Local gaps and next review milestone

1. **Obsolete-slot cleanup implemented in this branch.** After the new credential slot becomes active, `save()` deletes the inactive slot. A cleanup failure emits a sanitized warning and preserves the working connection; a subsequent successful save or disconnect retries cleanup. It does not revoke the shared Google grant. Controlled tests cover refresh cleanup and cleanup failure. [credentials.py](../../gmail/credentials.py), [OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices)

2. **Remote cleanup has a documented recovery limit.** If the pointer or active record cannot be read, disconnect cannot identify the active token to revoke; it still clears both slots and directs the owner to Google account permissions. Prior replaced grants are not individually revoked. Preserve that honest distinction and consider a cleanup journal only if the lifecycle requires it. [service.py](../../gmail/service.py)
3. **Configuration protection is not verified by code.** The client JSON is read from a configured path; ownership/permissions and whether a copy was committed are not enforced there. Directory creation modes do not repair pre-existing broad permissions. Keep client configuration outside source control with restricted access; a Desktop client secret is not a confidential-server secret, but user tokens remain sensitive. No secret inspection is needed to assess paths, permissions, or tracked filenames. [client.py](../../gmail/client.py), [credentials.py](../../gmail/credentials.py), [Desktop public-client model](https://developers.google.com/identity/protocols/oauth2/native-app)

These are focused lifecycle/configuration follow-ups, not a reason to move current tokens into a database or reconnect automatically. Review one milestone before implementation. The audited code supports the core documented local pattern; it does not establish complete Google policy compliance or prove that every external logging configuration is safe.

## Future hosted multi-user design

The following is a proposed design, not existing behavior:

- Introduce a connection metadata model with a foreign key to the authenticated application user, provider, stable provider subject when available, display email, OAuth client identifier, granted scopes, connection status, token expiry, consent/refresh/disconnect timestamps, secret reference, and optimistic version. Decide explicitly whether one user may connect multiple mailboxes; enforce the matching uniqueness rule. Scope every service operation and background job to the owning user and connection.
- Keep refresh tokens and any persisted access tokens in a managed secret store, or authenticated encrypted ciphertext with a KMS-managed key. Store ciphertext/envelope metadata or a secret reference in Django, never unprotected token JSON. Use distinct data keys across users; keep wrapping keys outside the database; restrict decryption to the worker/service identity, audit access, and design rotation, backups, and deletion together. Google's envelope-encryption guidance describes separate data and wrapping keys and IAM-governed key management. This application-layer scheme is a recommendation, not a claim that Google mandates this exact schema. [Cloud KMS envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption)
- If adopting OpenID Connect for stable Google identity, obtain and validate the ID token, including issuer/audience/expiry and the applicable nonce. Store `sub` as the Google identifier; Google cautions against email as the unique identifier. The existing Gmail-only profile flow does not currently obtain this OIDC identity; do not invent it from an email address. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
- Replace the global `TELEGRAM_OWNER_ID` credential lookup with authenticated owner/connection resolution and cross-user access tests. Replace filesystem locks with cross-worker coordination and versioned refresh writes. A refresh failure should mark the affected connection reconnect-required without exposing provider details. Encrypting tokens does not itself prevent cross-tenant access bugs.

## Hosted authorization migration

Register a Web application OAuth client and an exact HTTPS callback. Store its confidential client secret in managed secret storage. Begin authorization from an authenticated application session; bind unpredictable, short-lived, single-use state to that session and intended connection, then verify it before exchanging the code server-side. Request offline access for background work and validate granted scopes/account identity before activation. Preserve an existing refresh token when a response omits a new one for the same authorized connection; never reuse it across users or OAuth clients. Google's web-server guide documents HTTPS redirects, state checking, offline access, and refresh-token handling. [Web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)

Changing the credential store alone does not perform this migration. Do not upload the current Desktop credentials or replace their client ID in place. Obtain fresh authorization under the Web client and retain the local connection until the separately reviewed migration succeeds. For a broader hosted release, separately review restricted Gmail scopes, consent/verification, user-data disclosures, and retention requirements. [Restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)

## Additional current Google recommendation

Google now also recommends evaluating DPoP-bound refresh tokens, particularly for installed apps. This application currently uses bearer credentials with PKCE and Keychain; DPoP is not implemented. Treat support in the Google OAuth libraries and safe migration of the existing grant as a separate reviewed hardening task, rather than claiming complete coverage of every current recommendation. [Google best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices#sender-constrain_tokens_with_dpop)
